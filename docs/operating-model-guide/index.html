The Operating Model

From chat to agent systems — an interactive introduction

🔤 Prompt → ⚡ Skill → 🤖 Agent → 🏗️ Agent System
This repo uses a roles-over-skills model where specialized agents collaborate through explicit handoffs, durable work packets, and structured skills. The goal is that the right context is always available without the engineer having to remember to provide it.

Why This Exists

The Shift: From Chat to Agent Systems

Most developers start with AI as a chat interface — ask a question, get an answer. That works for small tasks, but it hits a ceiling fast.

💬 Chat-Based Agents

Limited memory between sessions. No role boundaries. No structured accountability for claims. Context resets every conversation. The human carries most state in their head.

Good for: quick Q&A, small edits, learning a new API.

🏗️ Agent Systems

Persistent context in work packets. Specialized roles with explicit handoffs. Evidence-based verification. Skills encode how work gets done — not just what gets done.

Good for: production code, multi-step tasks, team workflows.

Context Engineering over Prompt Engineering

Prompt engineering is about crafting a single input for one interaction — choosing words carefully to get a better response. It's stateless and per-request.

Context engineering is about designing the entire information environment that the AI operates in. It includes three layers in this repo:

  • Project rules (CLAUDE.md, AGENTS.md, .github/copilot-instructions.md) — loaded automatically by each tool; encode architecture rules, coding constraints, testing requirements
  • Skills (.agents/skills/) — reusable structured capabilities that encode how to do specific kinds of work; the AI activates them when relevant
  • Work packets (docs/work/<id>/) — durable task context that survives session boundaries; brief, plan, status, evidence, and handoffs in one place

The shift: instead of typing the perfect prompt every time, you build a system where the right context is always available.

The Autonomy Ladder

Not all AI usage is the same. Think of it as a ladder of increasing autonomy:

1–2 Autocomplete & chat Q&A Copilot inline, ChatGPT
3 Multi-file edits, runs commands Copilot Agent Mode, Cursor, Claude Code
4 Agent loop: plan → code → test → fix Claude Code + skills, Copilot + custom agents
5+ Agents do primary work, humans review Agent systems, orchestration

This repo operates primarily at Level 3–4, where the practical value is right now. The operating model is the framework that makes Levels 4–5 reliable.

Core Thesis: Designing systems that produce code

We are moving from writing code line by line to designing systems that produce code.

For engineers, this doesn't mean we stop understanding the domain. It means our job evolves. We become architects of process, not just authors of functions.

The operating model is that process architecture — it defines who does what, how context flows, and how claims are verified.

Foundations

Core Concepts

Three ideas underpin the entire operating model. Expand each to learn more.

🎭 Roles Over Skills — agents make better decisions when focused on a single objective

A "skill" is a reusable capability — like TDD, debugging, or code review. A "role" is an agent with a specific objective and accountability.

The key insight: role boundaries prevent conflicting objectives. A planner wants completeness; a developer wants simplicity. These pull in opposite directions. Combining them in one session leads to compromised work.

The handoff is the explicit moment where objectives change. It's a Markdown file with context, rationale, and done-when criteria — not a vague "take a look at this."

How it differs from one-agent-does-everything:

❌ Single agent

  • Plans and implements simultaneously
  • Judges its own work
  • Loses context across sessions
  • No accountability trail

✅ Roles-over-skills

  • Product-owner establishes shared understanding
  • Planner decomposes; developer implements
  • Verifier checks independently
  • Handoffs create an audit trail
🧠 Context Engineering — the right context is always available without the engineer remembering to provide it

Every AI session in this repo automatically receives context through three layers:

📋 Project Rules

Files like CLAUDE.md, AGENTS.md, and .github/copilot-instructions.md are loaded automatically by each tool. They encode architecture rules, coding constraints, testing requirements, and build commands.

⚡ Skills

Structured capabilities under .agents/skills/ encode how to do specific kinds of work. The AI activates them when relevant — like TDD for implementation or hypothesis-driven debugging for bugs.

📦 Work Packets

Durable task context under docs/work/<id>/ survives session boundaries. Brief, plan, status, evidence, and handoffs — all in one place, readable by any agent.

Skills are particularly valuable when the AI has little training data on your domain, or when you want work done a very specific way.

📁 Durable Work Packets — one fact has one durable home

Chat history is ephemeral. Work packets are not. For every non-trivial task, a packet lives at docs/work/<work-id>/ containing:

  • brief.md — the canonical shared-understanding record (product-owner owns it)
  • plan.md — the canonical execution plan (planner owns it)
  • status.md — current owner and next-action snapshot
  • evidence/ — durable proof: verification records, loop logs, hypotheses, optimization scorecards
  • handoffs/ — role-to-role transition records that point back to canonical files

The rule: one fact should have one durable home. Handoffs and chat reference canonical files instead of restating context. Tool-local scratch (like session state files) is temporary — it does not replace the work packet.

The repo CLI (python3 tools/cli.py new-work <id>) scaffolds this structure automatically.

Who Does What

The Roles

Twelve specialized roles, each with a single objective. Six form the core flow; seven are optional specialists that join when their trigger conditions are met. Not every role participates in every task.

Core Flow Roles Default Flow

🎯
product-owner
Human-facing control thread & delegation

The default entry point for every non-trivial task. Establishes shared understanding with the requester before delegating.

When active

  • Always — this is the default human-facing control thread
  • Task is non-trivial, ambiguous, multi-step, or involves specialists

Shared-understanding contract (align before delegating)

  1. Problem / desired outcome
  2. Scope
  3. Non-goals
  4. Constraints
  5. Acceptance criteria
  6. Delivery class: product development or non-productized tool
  7. Assumptions / open questions
  8. Code driver: user scenario, risk, spike, design intent, or external obligation

Responsibilities

  • Restate the request in outcome terms
  • Align on all eight shared-understanding fields above
  • Create and maintain brief.md and status.md
  • Choose the right specialist and hand off explicitly
  • Synthesize results back to the requester

Key rule

Do not delegate until the goal and done-when criteria are explicit.

🗺️
planner
Task decomposition & safe parallel lanes

Makes the next step smaller, safer, and more checkable. Decomposes ambiguous or risky work into a verifiable plan.

When to bring in

  • Scope is unclear or the request has multiple plausible implementations
  • Acceptance criteria are not yet concrete
  • Independent parallel work could shorten the critical path

Returns

  • A checkable plan.md with ordered lanes
  • Recommended next owner(s)
  • Blockers, merge points, and verification gates
🔨
developer
Smallest effective change

The implementation specialist. Works from the delegated brief, preserves scope, and follows TDD by default for product development.

Optimizes for

  • Smallest effective diff
  • Preserved behavior unless intentionally changed
  • Host-verifiable logic where practical
  • TDD-first for product development

Key rule

If the requested behavior is unclear, stop and hand the ambiguity back instead of guessing.

🔍
verifier
Evidence, not plausibility

The verification specialist. Assumes the implementation might be wrong and attempts falsification first.

Standard

Evidence, not plausibility. "Looks reasonable" is not "is demonstrated."

Returns

  • Verdict: demonstrated, disproved, or unresolved
  • Evidence gathered
  • Unverified areas and residual risk
  • Recommendation on whether to proceed
⚔️
reviewer
Hidden risk, complexity, weak evidence

Fires after implementation to critique the actual patch and evidence — looking for hidden risk, overengineering, and missing evidence. Not the same as red-team, which challenges the plan before implementation.

When to bring in early

  • The plan feels large
  • Multiple abstractions are being introduced
  • The change crosses platform boundaries
  • There is a temptation to "rewrite it cleanly"
🏛️
firmware-architect
Interfaces, HAL, migration, structure

Protects long-term structure: interface stability, HAL boundaries, migration shape, and timing correctness.

When to bring in

  • A hardware seam is missing
  • Platform code is leaking upward
  • A migration path is unclear
  • Interface stability matters more than immediate speed
  • The change affects timing, concurrency, or architecture

Optional Specialists Join When Needed

✍️
technical-writer
Reader-facing docs, release notes, migration guides

When to bring in

  • Release notes or changelog entries need curation
  • Migration or deprecation guidance is needed
  • Docs have drifted into duplication or unclear structure
🚀
release-manager
Version bump, release shape, go/no-go

When to bring in

  • SemVer impact or release readiness is disputed
  • Changelog, release notes, and evidence need a single final owner
  • The choice between pre-release, canary, and full release is unclear
🔌
integration-engineer
HIL, bench, environment reproducibility

When to bring in

  • HIL or bench setup is the critical bottleneck
  • The environment is flaky and needs reproducible setup
  • Repeated reruns can't distinguish product failures from environment failures
🛡️
red-team
Adversarial challenge of plans before implementation

When active

  • Medium/high-risk work, after planner writes plan.md
  • Before developer starts implementation

Returns

Structured findings with an approve / revise / escalate recommendation.

🔧
workflow-architect
Process evolution, role/skill improvements

When to bring in

  • The same workflow friction appears across multiple tasks
  • Role boundaries are repeatedly unclear in practice
  • A prompt, template, skill, or role may need to be created or refined
🔬
researcher
External domain investigation

When to bring in

  • Work references a specific external component, standard, SDK, or library
  • External assumptions have not been verified against current sources

Scope

Stops before option comparison or design begins — produces a durable research summary only.

In Practice

The Default Workflow

A non-trivial task typically flows through roles in this order. This is a common loop, not a strict pipeline — verifier, reviewer, firmware-architect, and researcher may join earlier when their trigger conditions are met.

sequenceDiagram participant U as 👤 Requester participant PO as 🎯 Product Owner participant PL as 🗺️ Planner participant RT as 🛡️ Red Team participant D as 🔨 Developer participant V as 🔍 Verifier participant R as ⚔️ Reviewer U->>PO: Describe desired outcome PO->>PO: Establish shared understanding PO->>PL: Hand off brief.md PL->>PL: Decompose into plan.md PL->>PO: Return plan + recommended owners Note over RT: (medium/high-risk only) PO->>RT: Challenge plan.md RT->>PO: Findings + approve/revise/escalate PO->>D: Delegate implementation D->>D: TDD: test → code → refactor D->>V: Hand off for verification V->>V: Attempt falsification V->>PO: Verdict + evidence PO->>R: Request review R->>PO: Risk assessment + findings PO->>U: Synthesize result
Understanding the handoff model

Each arrow in the diagram is a handoff — a structured Markdown file stored under docs/work/<id>/handoffs/. A handoff includes:

  • Destination role and rationale
  • Pointers to brief.md, plan.md, status.md
  • What changed since the previous owner
  • New assumptions, risks, or blockers
  • Requested next action
  • Done-when criteria for the recipient

Handoffs are delta-focused — they point to canonical files instead of restating all context. This prevents the "telephone game" where information degrades across handoffs.

When specialists join

The seven optional specialists join based on specific triggers:

  • red-team — when medium/high-risk work needs adversarial plan review before implementation starts
  • firmware-architect — when interfaces, HAL boundaries, migration shape, timing, or long-term structure matter
  • technical-writer — when release notes, migration guides, or substantial docs deserve their own lane
  • release-manager — when version bump, changelog finalization, or go/no-go needs a dedicated owner
  • integration-engineer — when HIL/bench setup, flashing, or environment stability is the bottleneck
  • workflow-architect — when repeated friction in the process itself needs investigation
  • researcher — when work references an external component not already characterized in the codebase
Parallel work: when and how

Multiple specialists may work in parallel, but only when the planner has made these things explicit:

  • Ownership boundaries — who owns which files/surfaces
  • Dependencies — what blocks what
  • Integration checkpoints — when parallel work merges
  • Isolation plan — separate worktrees or equivalent to avoid write conflicts

Without these, work stays serial. The coordination cost of vague parallel work exceeds the time savings.

Capabilities

Skills Catalog

A skill is a reusable, structured capability — it encodes how to do a specific kind of work. This repo has 37 canonical skills across six categories.

What is a skill, exactly?

A skill is a structured prompt that tells the AI how to approach a specific kind of work. Unlike a one-off prompt, skills are:

  • Reusable — checked into the repo, available to every session
  • Structured — with "when to use," "steps," "constraints," and "output format" sections
  • Composable — skills can be chained into sequences for different work types

You write a skill when: the AI doesn't have much training data on your domain, you want things done a very specific way, or you use the same prompt pattern more than once.

Two tiers

  • Repo skills shared — version-controlled under .agents/skills/, synced by tools/cli.py sync. The starter ships a canonical set; adopters add their own alongside them in the same directory.
  • Personal — stored globally (e.g. ~/.claude/skills/) or gitignored, individual productivity, no team expectation

🔭 Planning & Discovery

codebase-exploration

Map files, entry points, boundaries, and invariants before changing code.

When to use:

  • Exploring an unfamiliar area of the codebase
  • Tracing ownership, dependencies, or module boundaries
  • Finding test seams before making changes
planning

Produce a concrete, staged plan with explicit verification before implementation.

When to use:

  • Request is ambiguous or has multiple implementation options
  • Work crosses modules or layers
  • Risk needs to be understood before code changes
research

Structured external domain investigation — datasheets, specs, standards, errata, feasibility signals.

When to use:

  • A knowledge gap must be closed before planning is possible
  • Work references an external component, standard, or SDK

Stops before option comparison or design begins.

write-a-brief

Build a complete brief.md through structured discovery.

When to use:

  • Starting a medium or large feature
  • Problem space is not yet fully understood
  • A blank template is not enough — need guided discovery
grill-me

Stress-test a brief or plan through relentless structured interrogation.

When to use:

  • Product-owner wants to challenge a brief before delegation
  • Planner wants to challenge a plan before implementation
  • User explicitly says "grill me"

⚠️ Requirements & Risk

requirements-and-traceability

Capture stakeholder needs, explicit requirements, derived requirements, and their links to design and verification.

When to use:

  • Expected behavior is unclear or may drift across handoffs
  • Multiple stakeholders matter
  • Traceability is needed for safety, release, or systems work
risk-catalog

Maintain a project-level risk catalog with stable RK-NNN IDs, FMEA fields, and mechanical mitigation coverage checking.

When to use:

  • Safety-risk-scan produces findings worth tracking permanently
  • Requirements carry failure-mode implications
  • Verifying that cataloged risks have test-proven mitigations
safety-risk-scan

Enumerate likely failure modes and required mitigations for safety- or reliability-sensitive changes.

When to use:

  • Changing storage, control logic, sensor handling, or state machines
  • Behavior on timeout or reboot matters
  • Before merging safety-critical code
security-threat-modeling

Identify security threats, attack surfaces, and trust boundaries for firmware and connected-device changes.

When to use:

  • Adding connectivity, authentication, or OTA update paths
  • Storing secrets or adding external interfaces
scenario-traceability

Keep plain-English usage scenarios linked to tests with stable SC-NNN IDs and mechanical coverage checking.

When to use:

  • Starting a feature or writing acceptance criteria
  • Verifying that every stated user need has at least one covering test

📐 Design & Architecture

design-an-interface

Generate three or more radically different interface designs, then compare and recommend the deepest option.

When to use:

  • Implementing a new module, HAL boundary, or API surface
  • Interface shape will be hard to change later
interface-contract-design

Define stable module contracts with explicit inputs, outputs, failure modes, timing, and ownership.

When to use:

  • Introducing or changing a module boundary
  • Reshaping a HAL or service interface
  • Resolving ambiguity between callers and implementers
trade-study-and-decision-analysis

Compare viable options against explicit criteria and choose a justified direction.

When to use:

  • Multiple architectures, interfaces, or rollout shapes are plausible
  • Team needs evidence-based decision instead of intuition
hardware-abstraction

Keep direct hardware access behind a narrow seam and separate policy from mechanism.

When to use:

  • Application code touches peripherals directly
  • Platform migration is underway
  • Hardware details are leaking into business logic
ubiquitous-language

Extract domain terminology into a canonical glossary so the same term always means the same thing.

When to use:

  • Starting a new domain
  • Terminology confusion is causing miscommunication
  • Code mixes synonyms for the same concept

🔨 Implementation

tdd

Drive implementation with a failing test, the smallest passing change, and safe cleanup.

When to use:

  • Default for all product development work
  • Optional for non-productized tools when plan says so
bdd

Discover and formulate behavior through concrete examples before or alongside implementation.

When to use:

  • Shaping acceptance criteria or turning a brief into rules and examples
  • Mapping scenarios onto the test pyramid
  • Aligning product behavior before TDD begins
bounded-autonomy-loop

Run a narrow implementation slice as a fixed-budget self-correcting loop with explicit done-when criteria.

When to use:

  • Task is already well-scoped with stable objective
  • Automated checks can verify each pass
  • Loop can stop cleanly as complete, blocked, or budget exhausted
story-loop

Run a list of user stories autonomously, implementing each with the smallest effective change.

When to use:

  • Planner-defined story list has explicit acceptance criteria
  • Automated checks (tests, lint, build) can verify each story
tidy-first

Quick hygiene pass — naming, dead code, small duplication, lint fixes — without changing behavior.

When to use:

  • User says "clean up this code" or "tidy before feature work"
  • Target area is messy and needs low-risk prep first
refactoring

Perform behavior-preserving refactors with explicit invariants, staged edits, and regression gates.

When to use:

  • User asks to refactor, restructure, reorganize, or clean up code
  • External behavior must not change
simplify-without-behavior-change

Remove accidental complexity without changing externally visible behavior.

When to use:

  • Code feels overengineered or wrappers add little value
  • Flags or state paths are tangled
  • Before a refactor, to reduce noise first

✅ Verification & Quality

verification

Prove that the claimed change works and state clearly what remains unverified.

When to use:

  • A code change was made or a bug fix is claimed
  • Refactor or migration needs evidence
  • Before marking work as done
validation-planning

Plan how to show the work solves the real stakeholder need, not just that implementation passes tests.

When to use:

  • Product behavior changes or multiple user groups matter
  • Measures of effectiveness or performance need definition
  • Verification alone would not show fitness for purpose
simulation-harness-first

Bias toward deterministic host-side simulation and fake time/I/O before hardware-only iteration.

When to use:

  • Debugging is slow on hardware
  • Logic mixes hardware interaction and decision-making
  • You want fast deterministic test feedback
fault-injection-and-recovery

Exercise timeout, corruption, missing-device, reset, and other failure scenarios deliberately.

When to use:

  • Testing error paths or verifying recovery behavior
  • Checking fault tolerance or stress-testing failure handling
  • Confirming safe degradation under faults
hypothesis-driven-debugging

Debug by ranking concrete hypotheses and running discriminating checks.

When to use:

  • Bug is hard to localize or has many plausible failure points
  • Logs are noisy or misleading
  • Trial-and-error edits haven't worked
operation-cost-optimization

Optimize performance, endurance, churn, or footprint by measuring the real cost driver.

When to use:

  • Flash erases/writes, RAM/flash usage, heap traffic, or I/O dominate
  • Need explicit cost model with weights and measured reductions
resource-budget-review

Review RAM, flash, stack, CPU, latency, and logging impact as part of the change.

When to use:

  • Changing allocation patterns, buffers, queues, or state machines
  • Adding platform features or diagnostics
  • Moving behavior into a tighter execution context

🚀 Operations & Process

release-readiness

Prepare or assess a release using explicit SemVer classification, release shape, and evidence gates.

When to use:

  • Version bump or release readiness decision needed
  • Pre-release vs full release choice is unclear
  • Changelog shaping or go/no-go decisions
lab-and-hil-reproducibility

Make bench, HIL, flashing, and cross-component integration checks reproducible and auditable.

When to use:

  • Hardware identity, fixture setup, or flashing steps need a repeatable workflow
  • Flaky-lab triage or product-vs-environment failure classification
observability-and-diagnostics

Add or refine the minimal logs, counters, asserts, and traces needed to verify and support the system.

When to use:

  • A bug is hard to localize or failures are silent/ambiguous
  • A migration needs confidence signals
  • Adding observability before a risky change
firmware-migration

Move from legacy platform structure to a target structure in small, verified, reversible steps.

When to use:

  • Migrating to a new MCU, RTOS, HAL, or transport layer
  • Replacing legacy platform glue or porting firmware
postmortem

Run a structured blameless postmortem after an incident, outage, or significant unexpected failure.

When to use:

  • Production issue occurred or fleet-wide update failed
  • Safety-critical bug escaped or systemic process failure
docs-adr-updates

Keep README, CHANGELOG, architecture notes, and ADRs aligned with the implemented system.

When to use:

  • A design decision, interface, or API changed
  • A migration path was introduced or docs are stale
  • Release-facing behavior changed
workflow-evolution

Improve the roles-and-skills system from evidence in durable work artifacts.

When to use:

  • Repeated friction, unclear role boundaries, or stale prompts
  • A possible new skill or role needs a disciplined workflow change
plan-red-team

Challenge a completed plan.md before implementation starts.

When to use:

  • Work is medium/high-risk
  • Product-owner needs adversarial pass on assumptions, sequencing, and dependencies

Guardrails

Do / Don't

Behavioral defaults that keep the operating model effective. These are reinforced by project rules loaded into every session.

✅ Do

  • Establish shared understanding before delegating
  • Keep one active human-facing owner (product-owner)
  • Use explicit handoffs with done-when criteria
  • Store durable context in work packets, not chat
  • Follow TDD for product development work
  • Use the test pyramid: mostly unit/simulation, fewer integration, fewest HIL
  • State what was not verified on real hardware
  • Prefer simulation-first before hardware-only debugging
  • Keep hardware access behind narrow interfaces
  • Make timing, units, and failure behavior explicit
  • Prefer remove before add, inline before abstract
  • Use the CLI for work-packet scaffolding

❌ Don't

  • Delegate before restating the real problem
  • Let specialists negotiate requirements directly with the requester
  • Widen scope silently ("we're already in the file")
  • Claim success without evidence
  • Let the implementer declare victory
  • Run parallel work without explicit ownership boundaries
  • Skip TDD without making that decision visible
  • Introduce abstraction before naming its real pressure
  • Treat integration as a late phase
  • Write code traceable to no driver (scenario, risk, spike, design intent, or obligation)
  • Keep handoffs only in chat instead of in-repo Markdown
  • Treat tool-local session files as canonical work packets
Common anti-patterns explained
  • Delegating raw user text — The product-owner should restate the request in outcome terms first. Passing vague text to a specialist produces vague results.
  • Copying context everywhere — Instead of copying scope and risks into every handoff, use one canonical work packet and reference it. One fact, one home.
  • The implementer declares victory — The developer should not be the one who decides the work is done. The verifier checks independently. Separation of concerns applies to judgment, not just code.
  • Treating resource use as post-processing — Stack, RAM, flash, CPU, latency, and watchdog behavior are part of correctness, not something to check after the feature is "done."
  • Unbounded autonomy loops — Bounded autonomy requires explicit budget and stop states. Without them, a loop becomes an unbounded retry habit on ambiguous work.

Practical

Getting Started

Three steps to go from zero to a working task with the operating model.

Validate your setup

Run the doctor command for your tool to check that all project rules, skills, and agent definitions are correctly wired:

python3 tools/cli.py doctor --tool all
python3 tools/cli.py sync
python3 tools/cli.py sync --check

Create a work packet

Scaffold a new work packet with the CLI. This creates brief.md, plan.md, status.md, and the evidence/ and handoffs/ directories:

python3 tools/cli.py new-work my-first-task
python3 tools/cli.py check-work my-first-task

Start with the product-owner

Open your AI tool and ask the product-owner agent to summarize the current instructions and available skills. Then describe your desired outcome — the product-owner will guide you from there.

# In Copilot CLI or Claude Code:
# Start by talking to the product-owner agent
"Summarize the current instructions and available skills"

Cross-tool compatibility

The same role model is shared across Claude Code, GitHub Copilot, and OpenAI Codex. Canonical definitions live in .agents/agents/*.toml and .agents/skills/. Running python3 tools/cli.py sync regenerates tool-specific files from these canonical sources.

Role names and skill names stay aligned across tools so prompts and handoffs remain portable.

What to do on Monday morning
  1. Pick a real task — something small but non-trivial. A bug fix or a small feature.
  2. Create a work packet — python3 tools/cli.py new-work <task-name>
  3. Fill the brief — Describe the problem, scope, non-goals, and acceptance criteria in brief.md.
  4. Let the product-owner drive — Start your AI tool and let the product-owner establish shared understanding, then delegate to planner and developer.
  5. Observe the handoffs — Watch how the brief turns into a plan, then code, then verification. Each step is traceable.
  6. Check the result — python3 tools/cli.py check-work <task-name>

Start small. The operating model works best when you trust it on something manageable first, then scale up.
