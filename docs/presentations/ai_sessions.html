🧩 Session 1

Copilot: More Than Autocomplete

Let's start at the beginning. And I want to be clear — when I say Copilot, I mean the full tool, including its agent mode. It's much more than the inline suggestions you might have seen.

Copilot in 2026

  • Inline autocomplete (Level 1–2)
  • Chat panel with codebase context
  • Agent Mode — multi-file edits, terminal commands, iterative fixes (Level 3)
  • copilot-instructions.md — project rules the AI reads automatically
Copilot in 2026 has several modes. The inline autocomplete you know. A chat panel. But the big one is Agent Mode — it can edit multiple files, run terminal commands, and iterate on fixes. That's Level 3 on our ladder. ▶ And here's something most people don't know: you can put a file called copilot-instructions.md in your repo, and Copilot reads it automatically every session. That means you can encode your project's coding standards, architecture rules, and constraints. The AI knows your rules before it writes a single line. That's the beginning of context engineering, and we'll come back to it. ▶ The same idea exists for Claude Code — it's called CLAUDE.md — and for Codex, it's an agents directory. Different tools, same principle: project rules live in the repo.

✅ Works well

  • Small, focused functions
  • Clear intent in comments
  • Good naming
  • Iterating on specific files

❌ Doesn't work

  • Large files with no structure
  • Vague tasks
  • "Write my whole module"
  • Hardware timing without constraints
When does it work well? Small, focused functions. Clear intent. Good naming. Iterating on specific files. When does it fail? Large files with no structure. Vague tasks. "Write my whole module." And — this is critical for us — anything involving hardware timing without explicit constraints. Karpathy describes LLMs as having "jagged intelligence" — they can solve complex math but fail at "which is greater, 9.11 or 9.9?" They're brilliant and stupid in unpredictable ways. Research on embedded AI agents found that "code that compiles successfully may still fail when deployed on real devices because of timing constraints, peripheral initialization requirements, or hardware-specific behaviors."

Example

// Add timeout handling to I2C transfer
// No heap
// Must be ISR-safe
// Budget: complete within 10ms
"Nudge, don't outsource"
Here's a practical example. Four comment lines. Task, constraint, safety requirement, timing budget. That's all the AI needs. You've told it what to do and what the boundaries are. ▶ The key phrase: "Nudge, don't outsource." You're steering. You're the pilot. As Yegge puts it: "You know what you want before the AI writes it. You already have a vision for how you would write this by hand."

Copilot is not here to think for you. It's here to accelerate what you already understand. If you don't understand the code it generates, that's a red flag — not for the tool, but for the task. Prompting & Roles

Session two. We move beyond autocomplete into directing AI behavior.

The Shift

From autocomplete → directing behavior

The shift here is significant. We're telling the AI who to be, what to focus on, and how to respond. Karpathy coined "vibe coding" — his exact words: "you fully give in to the vibes, embrace exponentials, and forget that the code even exists." That got four and a half million views. But by late 2025, even Karpathy was saying vibe coding was becoming passé for professional work. For firmware, we definitely need more structure.

- race conditions
- memory safety

Output:
- issues + fixes

Prompt Structure

"Prompts are specifications, not questions"
Here's the formula. Role, context, task, constraints, output. ▶ Think of prompts as specifications, not questions. You're not asking AI a question — you're writing a spec. Just like you wouldn't write a vague requirement for a peripheral driver, don't write a vague prompt.
Giving a role compresses expertise

"We stop treating AI like Google — we treat it like a junior engineer with context"

When you give AI a role, you compress expertise. Karpathy describes LLMs as "a bit like a coworker with anterograde amnesia — they don't consolidate or build long-running knowledge." So you have to front-load the expertise into every interaction. Saying "you are a senior embedded firmware engineer" activates a completely different set of patterns than saying nothing. ▶ We stop treating AI like Google. We treat it like a junior engineer who needs context to do good work.

🧩 Session 3

Skills

Session three: skills. Everything before this was useful. Everything after this is transformational.

Why Skills?

A skill is a reusable, structured capability

You write a skill when:

  • The AI doesn't have much training data on your domain
  • You want things done a very specific way
  • You use the same prompt pattern more than once
Why skills? A skill is a reusable, structured capability. But when do you actually need one? ▶ Three situations. First: when the AI doesn't have much training data on what you're doing. Niche hardware, proprietary protocols, your company's specific architecture. The AI is guessing — a skill gives it the answers. Second: when you want things done a very specific way. Your review checklist, your TDD flow, your debugging methodology. Third: when you use the same prompt more than once. If you typed it twice, make it a skill. The embedded benchmark study backs this up: without expert-crafted skills, AI solved sixty-seven percent of embedded tasks. With skills — ninety-seven percent. The skill is what closes that gap.

What a Skill Looks Like

# SKILL: Hypothesis-Driven Debugging

## When to use
Debugging a symptom that has multiple possible causes

## Process
1. Restate the symptom as an observable, falsifiable claim
2. List candidate hypotheses ranked by likelihood
3. For each hypothesis, name a discriminating check
4. Run the cheapest discriminating check first
5. Update rankings after each result
6. Stop when one hypothesis is confirmed

## Key rule
Instrument first, then form hypotheses.
Do not change configs speculatively.
Here's a real skill. This is a hypothesis-driven debugging skill. It defines when to use it, the exact process to follow, and a key rule. When AI follows this skill, it produces a documented trail: symptom, ranked hypotheses, discriminating checks, and results. Every debugging session follows the same rigor. This is just a markdown file. Nothing fancy. You put it in a folder, and the AI reads it when it's relevant.

Community Skill: "Grill Me"

# SKILL: Grill Me

Matt Pocock — github.com/mattpocock/skills

Here's a fun one from the community. Matt Pocock — a TypeScript educator with a huge following — created a skill called "Grill Me." You say "grill me about this plan" and the AI interrogates you about every decision, every assumption, every edge case. It supplies a recommended answer with each question so you're not starting from scratch. And if it can verify something by reading your codebase, it reads the code instead of asking. Pocock has a whole workflow built around skills. He has a "write a PRD" skill that interviews you through five steps to create a product requirements document. A "PRD to issues" skill that breaks it into GitHub issues. And then he feeds those into a Ralph Loop — which I'll talk about later — for autonomous implementation. His full chain is: idea, write a PRD, PRD to issues, Kanban board, Ralph loop, manual QA.

CLI: The Agent's Natural Habitat

Session four. We move out of the chat window and into the command line. But not the way you might think.

The Shift

From chat → the AI runs the commands

Here's the shift. You don't pipe text into AI. You tell the AI what you want, and it runs the commands itself. Claude Code, Copilot Agent Mode, Cursor — they all have terminal access. They can run your build, read the errors, and fix the code. In a loop.

What This Actually Looks Like

You: "Run the host tests and fix any failures"

Agent: Running `ctest --test-dir build/host-tests`...
       2 tests failed: test_pid_clamp, test_fault_latch
       Reading test source...
       The PID clamp test expects output ≤ 1.0 but
       the implementation doesn't clamp negative values.
       Fixing app/src/control/pid.c...
       Re-running tests...
       All 16 tests pass. ✅
This is what it actually looks like. You say "run the host tests and fix any failures." The agent runs ctest. Two tests fail. It reads the test source, reads the implementation, identifies the bug, fixes the code, re-runs the tests. All green. You review the diff and commit. This is Level 3 on our autonomy ladder. The AI is using tools — read, write, execute — not just generating text. And LLMs are remarkably good at this. They understand command-line interfaces naturally because CLI tools have clear inputs, outputs, and error messages. It's structured text, which is exactly what LLMs are good at.

LLMs Are Great at Building CLI Tools

  • Ask AI to build a CLI tool → it does it well
  • Then the AI can use its own tools
  • CLI + Skill = powerful combo

▶ Here's a powerful pattern. LLMs are really good at building CLI tools. Clean input, clean output, clear error codes. So you ask the AI to build a tool, and then the AI uses its own tool in future sessions. ▶ In the project I'll show you later, the AI built a CLI tool that checks scenario coverage, risk mitigation, and agent sync. All of these return exit code 1 on failure — which means they work in CI too. ▶ The combination of CLI plus skill is where it gets powerful. The skill tells the AI the methodology. The CLI gives it the tools to execute that methodology. Run the tests. Check the coverage. Validate the layout. The AI orchestrates all of it.

🧩 Session 5

Context Engineering

The most underrated skill

Session five. Context engineering. MIT Technology Review titled their year-end piece "From vibe coding to context engineering." Gartner declared: "Context engineering is in, and prompt engineering is out." ▶ This is where the industry is heading. And firmware engineers have a natural advantage.
Context quality > Model quality
Context quality matters more than model quality. A mediocre model with great context outperforms a frontier model with bad context. Anthropic's engineering team published a guide called "Effective Context Engineering for AI Agents" — their core message: build dynamic systems that provide the right information, in the right format, at the right moment. Not "write a better prompt." Build a system that assembles the right context automatically.

Project Rules Files

The files

  • CLAUDE.md — Claude Code reads this
  • AGENTS.md — defines roles & workflow
  • copilot-instructions.md — Copilot reads this
  • .cursor/rules/ — Cursor reads these

What goes in them

  • Architecture rules
  • Coding constraints (no heap, ISR-safe)
  • Testing requirements (TDD, simulation-first)
  • Project layout expectations
  • Build & test commands

These files live in your repo. Every AI session starts with the right context automatically.

Here's what context engineering looks like in practice. Every major AI tool reads a project rules file. Claude Code reads CLAUDE.md and AGENTS.md. Copilot reads copilot-instructions.md. Cursor reads files in a .cursor/rules directory. ▶ These files live in your repo, version-controlled, shared with the team. Every AI session starts with the right context. The AI knows your coding standards, your architecture rules, your test commands — before it writes a single line. You set it up once and it works for every engineer on the team, every session.

What Context Engineering Looks Like

❌ Vibe coding

  • Dump entire repo
  • Hope AI figures it out
  • Retry until it works

✅ Context engineering

  • Project rules in repo
  • Relevant files only
  • Explicit constraints
  • Working examples
"Curate, don't dump"
The contrast. Vibe coding: dump the repo, hope for the best, retry until something works. Context engineering: project rules in the repo, curated relevant files, explicit constraints, working examples. ▶ Curate, don't dump. Your context should be like a well-written bug report — everything the reader needs, nothing they don't.

Debugging with AI

This is where firmware teams lean in

Session six — debugging with AI. This is where firmware teams really lean in. ▶ Because debugging is hard, time-consuming, and it's where AI gives you the biggest immediate payoff.
AI is a hypothesis generator
AI is a hypothesis generator. It doesn't debug for you. It generates hypotheses faster than you can think of them. Instead of staring at a log file for an hour, you get five ranked root causes in ten seconds. Then you go test them.

Debug Loop

Same debug loop you already use. Observe, hypothesize, test, refine. AI supercharges the hypothesis step. It's read millions of bug reports and debug sessions. But the test step is still yours — AI does not validate. You do.

Key Insight: Durable Evidence

# HYP-001: I2C timeout exceeds control loop budget

## Symptom
Control loop stalls after 30+ minutes of operation

## Hypotheses (ranked)
1. I2C sensor timeout exceeds 10ms budget  ← CONFIRMED
2. Watchdog feed thread starved
3. Stack overflow in fault handler

## Discriminating check
Instrumentation around i2c_transfer():
measured worst-case = 14ms > 10ms budget

⬆️ This lives in the repo, not in a chat window.

Here's where it gets really powerful. This is a hypothesis document. Symptom, ranked hypotheses, discriminating checks, and the result. This document lives in the repo. Not in a chat window that disappears when you close the tab. Not in someone's memory. In a markdown file under your project's evidence directory. Anyone can review the reasoning later. When the next engineer hits a similar problem, the investigation is right there. That's the difference between debugging in chat and debugging with a system.
⚠️ AI does NOT validate — you do

"Logs are gold — invest in structured logging"

One more time. AI does not validate. You do. Never trust an AI diagnosis without evidence. ▶ And logs are gold. The more structured logging you have, the more AI can help you. Invest in good logging — it pays dividends when debugging with AI.

🧩 Session 7

Agents & Autonomous Loops

Session seven. Agents and autonomous loops. This is where AI goes from a tool you use to a process that runs.

Definition

graph LR S["⚡ Skill"] --> |"+"| P["📋 Process"] P --> |"+"| L["🔁 Loop"] L --> A["🤖 Agent"] style S fill:#1a1a2e,stroke:#58a6ff,color:#fff style P fill:#1a1a2e,stroke:#58a6ff,color:#fff style L fill:#1a1a2e,stroke:#58a6ff,color:#fff style A fill:#16213e,stroke:#3fb950,color:#fff,stroke-width:3px

An agent = an LLM with access to tools (read, write, execute) and the ability to loop

What is an agent? Simply: an LLM with access to tools — read files, write files, run commands — and the ability to loop. A skill tells it what to do. A process tells it how. A loop means it iterates. That's the key difference between a chatbot and an agent. A chatbot answers. An agent works.

The Ralph Loop

graph TD S["📋 Pick next story"] --> I["👨‍💻 Implement"] I --> C["🧪 Run checks"] C -->|"pass"| CM["✅ Commit + mark done"] C -->|"fail"| F["🔧 Fix based on errors"] F --> C CM --> S CM -->|"all stories done"| DONE["🏁 Complete"] style S fill:#1a1a2e,stroke:#58a6ff,color:#fff style C fill:#1a1a2e,stroke:#58a6ff,color:#fff style DONE fill:#1a1a2e,stroke:#3fb950,color:#fff

Named after Ralph Wiggum — relentlessly failing but persistent. Popularized by Matt Pocock & the aihero.dev community.

The most famous agent loop right now is the Ralph Loop — named after Ralph Wiggum from the Simpsons. Relentlessly failing but persistent. The pattern is simple: pick the next story from a list. Implement it. Run checks — type check, tests, build. If checks pass, commit and mark the story done. If checks fail, read the errors, fix the code, run checks again. Repeat until all stories pass or you hit a max iteration budget. Matt Pocock popularized this with his ralph.sh script for Claude Code. It's simple but effective. You give it a list of user stories, and it works through them one by one, autonomously.

github.com/karpathy/autoresearch — open-sourced March 2026

And here's the bleeding edge. Karpathy open-sourced autoresearch just a few weeks ago. About 630 lines of Python. It gives an AI agent a training script, lets it modify the code, trains for five minutes, evaluates whether the result improved, and loops. Karpathy's vision is a "swarm of agents collaborating at increasing model scales, with humans optionally contributing on the edges." That's the future. But for us, today, the practical version is simpler: bounded loops with clear stop conditions.

Bounded Autonomy

The key to making loops safe is bounding them. Before the agent starts, you define the objective, the checks it must run every pass, and a fixed budget. It works, checks, and either completes, or hits the budget and stops. It never goes off into the weeds. This is important because — and I want to be honest about this — agents don't always follow instructions perfectly. They drift. They get creative in ways you didn't ask for. Bounded autonomy is how you keep them useful without losing control. Set a budget, require checks every iteration, and escalate when something is unclear instead of looping harder.
Agents loop — they don't just answer

"But they don't always follow the script — that's why we bound them"

Agents loop — they don't just answer. When you see an agent working through a problem, it feels like watching a junior engineer work through a checklist. Except at machine speed. ▶ But — and Yegge makes this point with his "vampire burnout" concept — you can only supervise agents for about three good hours a day before exhaustion sets in. And agents don't always follow the script perfectly. They approximate your instructions, they drift, they occasionally do something unexpected. That's why bounded autonomy matters — clear objectives, fixed budgets, mandatory checks, and escalation when stuck.

🧩 Session 8

Roles: One Hat at a Time

Session eight. We go from one agent to many specialized agents.

Why Roles?

Humans wear many hats.
Agents are more effective wearing one at a time.
Here's the key insight about agent roles. We as humans are good at wearing many hats — we plan, code, test, and review, often in the same hour. But agents are more effective when they wear one hat at a time. When you ask an AI to be a planner AND a developer AND a reviewer in one session, it compromises on all three. When you tell it "you are a reviewer — your only job is to find problems" — it goes deep. Separation of concerns isn't just for software architecture. It's for AI architecture too.

Example: Agent Team Flow

graph LR PO["👤 Product Owner"] --> PL["📋 Planner"] PL --> DEV["👨‍💻 Developer"] DEV --> VER["✅ Verifier"] VER --> REV["🔍 Reviewer"] style PO fill:#16213e,stroke:#58a6ff,color:#fff,stroke-width:3px style DEV fill:#1a1a2e,stroke:#58a6ff,color:#fff style VER fill:#1a1a2e,stroke:#3fb950,color:#fff

+ optional specialists: researcher, red-team, firmware-architect, safety-auditor...

Here's what a role flow looks like. Product owner establishes what we're building and why. Planner breaks it into checkable steps. Developer implements. Verifier independently checks. Reviewer attacks hidden risk. And you can activate specialists on demand — a researcher when you need datasheet information, a red team to adversarially challenge a plan, a firmware architect when interfaces matter. Each role has one job and returns results to the product owner, who keeps the thread coherent.

Being Honest About Agents

What works

  • Focused single-role tasks
  • Clear done-when criteria
  • Small, bounded slices
  • Skills for domain guidance

What doesn't (yet)

  • Agents drift from instructions
  • Context windows force session breaks
  • Turn budgets exhaust mid-task
  • Creative "helpfulness" = scope creep
Let me be honest about where agents are today. They work well on focused, single-role tasks with clear criteria and small slices. Skills help a lot for domain-specific guidance. But they also drift from instructions. They run out of context window. Their turn budgets exhaust mid-task on larger slices. And they have a frustrating tendency toward creative "helpfulness" — which is really just scope creep in disguise. The fix isn't to avoid agents. It's to bound them properly, keep slices small, and always review what they produce. This is a tool that amplifies your judgment, not one that replaces it.
"One agent = one responsibility"

Coordination is the system
One agent, one responsibility. And coordination is the system. ▶ The value isn't in any single agent — it's in how they work together. The handoffs, the checks, the feedback loops. This mirrors how we already work as a team.

🧩 Session 9

Systems Thinking

Session nine. The big picture.

The Big Shift

From writing code → designing systems of work

The biggest shift of all. We go from writing code to designing systems of work. Yegge predicts the IDE will be gone by 2026, replaced by agent interfaces. Whether or not that's true, the direction is clear. For firmware, this doesn't mean the code doesn't matter. It means the system that produces and validates the code is what we invest in.

Key Ideas

  • Validation > Generation
  • Feedback loops
  • Decomposition
Three ideas. ▶ Validation is more important than generation. AI generates code all day. Your value shifts toward defining "correct" and proving it. The Stack Overflow data confirms this — trust is going down. ▶ Feedback loops. CI results feed back. Skill refinement feeds forward. ▶ Decomposition. Break big problems into small ones, each with its own agent, skill, and verification.

🧱 Final Takeaways

Let me wrap up.

The 12 Rules

  1. Give the agent a role
  2. Add constraints
  3. Keep tasks small
  4. Ask for process
  5. Build skills
  6. Put project rules in the repo
  7. Reuse everything
  8. Verify outputs
  9. Think in bounded loops
  10. Use specialized roles
  11. Context matters most
  12. Design systems, not prompts
Twelve rules. One — give the agent a role. Two — add constraints. Three — keep tasks small. Four — ask for process, not just answers. Five — build skills from prompts you reuse. Six — put project rules in the repo: CLAUDE.md, copilot-instructions, AGENTS.md. Seven — reuse everything. Eight — always verify. Nine — think in bounded loops with budgets and stop conditions. Ten — use specialized roles, one hat at a time. Eleven — context matters more than model quality. Twelve — design systems, not prompts.

What's Different for Firmware

  • Timing matters — AI doesn't understand budgets unless you tell it
  • Hardware is real — compilation ≠ correctness on device
  • We have an advantage — we already think in constraints
  • HIL as CLI — when tests are commands, agents can run them
▶ What's different for firmware? Timing matters — AI doesn't know your control loop budget unless it's in the constraints. ▶ Hardware is real — code that compiles may not work on device. ▶ But we have an advantage. Firmware engineers already think in constraints. ISR safety, memory budgets, timing. That constraint-thinking is exactly what makes AI effective. We're naturally good at context engineering. ▶ And when your HIL tests are CLI commands, agents can run them — closing the loop between code and hardware faster than ever.
"We are not just using AI — we are extending it with our engineering system"
We are not just using AI. We are extending it. With our skills. With our project rules. With our engineering methodology. The AI model is powerful but generic. What makes it powerful for firmware, for Össur, for bionics — is what we build on top of it. That's our competitive advantage. Not the model. The system around it.
