The Job Is Changing

We are moving from

writing code

to

designing the workflow that produces code

For firmware, the code still matters, but the way we produce it is changing

This is probably the main idea underneath the whole series. ▶ Traditionally, a lot of our value came from writing the code directly. ▶ More and more, part of the job becomes designing the workflow that produces the code: the prompts, the constraints, the checks, the review loops, and eventually the agents. ▶ For firmware, this does not mean the code stops mattering. It means the process around producing and validating that code starts to matter much more.

🧩 Session 2

Copilot: More Than Autocomplete

Most people still think of Copilot as the little suggestion box in VS Code. That's the simple version. What I mean in this session is the larger tool around that, especially agent mode. That's a very different thing in practice.

Copilot in 2026

  • Inline autocomplete (Level 1–2)
  • Chat panel with codebase context
  • Agent Mode — multi-file edits, terminal commands, iterative fixes (Level 3)
  • copilot-instructions.md — project rules the AI reads automatically
The first two items are familiar: inline autocomplete and chat. ▶ The big jump is agent mode. Now it can edit multiple files, run commands, and iterate. That's level 3 on the ladder. ▶ And the other important idea is that the rules live in the repo. Different tools use different filenames, but the principle is the same. You set it up once, and the AI starts with your constraints already in view.

✅ Works well

  • Small, focused functions
  • Clear intent in comments
  • Good naming
  • Iterating on specific files

❌ Doesn't work

  • Large files with no structure
  • Vague tasks
  • "Write my whole module"
  • Hardware timing without constraints
Karpathy has a good phrase for this: "jagged intelligence." These models can do something surprisingly sophisticated in one moment, then fail at something embarrassingly simple in the next. For firmware, that matters even more, because code that compiles can still fail on hardware for all the usual reasons: timing, peripheral init, device-specific behavior. The model does not know your control loop budget unless you tell it. So tell it.

Tell It What Matters

// Add timeout handling to I2C transfer
// No heap
// Must be ISR-safe
// Budget: complete within 10ms
"Nudge, don't outsource"
This is a good example of how little you sometimes need. Four short lines: the task, the constraint, the safety requirement, and the timing budget. ▶ The mindset I like is: nudge, don't outsource. You're still the pilot. You already know what good looks like. You're just giving the model the boundaries it needs to move faster.

The Copilot Loop

graph LR E["👨‍💻 Engineer"] --> C["💬 Intent"] C --> CP["🤖 AI"] CP --> R["👁️ Review"] R --> CM["✅ Commit"] CM -.-> E style E fill:#1a1a2e,stroke:#58a6ff,color:#fff style CP fill:#16213e,stroke:#58a6ff,color:#fff,stroke-width:3px style CM fill:#1a1a2e,stroke:#3fb950,color:#fff

"Copilot is not here to think for you — it's here to accelerate what you already understand"

The loop is simple: you express intent, the AI generates something, and then you review it. ▶ The important part is the review step. Don't blindly accept it. If the generated code is hard to reason about, that's usually a sign the task needs to be made smaller or more explicit.

🧩 Session 3

Prompting & Roles

This is where we stop reacting to whatever the model gives us and start shaping its behavior more deliberately.

Directing Behavior, Not Guessing

From autocomplete → directing behavior

"Vibe coding was always for throw-away scripts. Firmware is not that." — Karpathy (paraphrased)
Karpathy popularized the phrase "vibe coding," and it took off because it captured a real feeling: just ask for something, keep going, and don't think too hard about the code. But even he framed that as something for throw-away scripts and quick demos. Firmware is not that. We need more structure, and the good news is that structure usually makes the tool much more useful anyway.

Bad prompt

"Review this"

Good prompt

Role: Senior embedded firmware engineer
Context: Cortex-M, no heap, ISR-safe
Task: Review this module
Focus:
- race conditions
- memory safety
- edge cases
Output:
- issues + fixes

More prompt patterns: prompts.chat

This is the same model looking at the same code. The only real difference is how you asked. "Review this" gets you generic feedback. The structured version is much more likely to surface real issues, like race conditions or missing ISR guards. And if you want a library of prompt patterns to steal from, prompts.chat is worth bookmarking.

Prompt Structure

graph LR R["🎭 Role"] --> CT["📋 Context"] CT --> T["🎯 Task"] T --> CO["⚠️ Constraints"] CO --> O["📤 Output"] style R fill:#1a1a2e,stroke:#58a6ff,color:#fff style CT fill:#1a1a2e,stroke:#58a6ff,color:#fff style T fill:#1a1a2e,stroke:#58a6ff,color:#fff style CO fill:#1a1a2e,stroke:#58a6ff,color:#fff style O fill:#1a1a2e,stroke:#58a6ff,color:#fff
"Prompts are specifications, not questions"
The basic structure is simple: role, context, task, constraints, and output format. ▶ The important mental shift is to treat prompts like specifications, not questions. You wouldn't hand a vague requirement to someone writing a peripheral driver. Same idea here.
Giving a role compresses expertise

"We stop treating AI like Google — we treat it like a junior engineer with context"

Karpathy has a line I like here: LLMs are a bit like a coworker with anterograde amnesia. They can be useful, but they don't carry stable long-term context the way a real teammate does. ▶ So when you give the model a role, you're front-loading the expertise for that session. "You are a senior embedded firmware engineer on a Cortex-M with no heap" activates a very different pattern than saying nothing. The role is not decoration.

🧩 Session 4

Skills

Everything up to now has been useful. This is where it starts becoming reusable.

Why Skills?

A skill is a reusable, structured capability

You write a skill when:

  • The AI doesn't have much training data on your domain
  • You want things done a very specific way
  • You use the same prompt pattern more than once
I think there are three good reasons to write a skill. One: the domain is niche, and the model is unlikely to know it well. Two: you want something done in a very specific way. Three: you find yourself repeating the same prompt. ▶ And the benchmark behind this is hard to ignore. Without expert-crafted skills, AI solved 67% of embedded tasks. With skills, that went to 97%. The skill is what closes that gap.

What a Skill Looks Like

# SKILL: Hypothesis-Driven Debugging

## When to use
Debugging a symptom that has multiple possible causes

## Process
1. Restate the symptom as an observable, falsifiable claim
2. List candidate hypotheses ranked by likelihood
3. For each hypothesis, name a discriminating check
4. Run the cheapest discriminating check first
5. Update rankings after each result
6. Stop when one hypothesis is confirmed

## Key rule
Instrument first, then form hypotheses.
Do not change configs speculatively.
This is a real skill I use. It's just a markdown file. But when the AI follows it, every debugging session leaves the same trail: symptom, ranked hypotheses, discriminating checks, and the result. And that evidence lives in the repo instead of disappearing in a chat window.

Community Skill: "Grill Me"

# SKILL: Grill Me

Interview the user relentlessly about every aspect
of this plan until we reach a shared understanding.

- Traverse the decision tree branch by branch
- Ask one probing question at a time
- Supply a recommended answer with each question
- If you can verify something by reading the codebase,
  read the code directly instead of asking

Matt Pocock — github.com/mattpocock/skills

Matt Pocock built this one, and it's a good example because the behavior is very clear. You say "grill me about this plan" and the AI starts pushing on the assumptions, the edge cases, and the failure modes. It also gives you a recommended answer with each question, so you're not starting from a blank page. And if it can verify something by reading the codebase, it does that instead of asking you.

There is now a whole ecosystem around this. You can install skills from GitHub, browse public ones, or write your own. The part I like is that the format is open. A `SKILL.md` file is just a markdown file. It isn't locked to one vendor, and it can live in the repo with the rest of your engineering system.
"If you use a prompt twice → make it a skill"

Skills encode how we think, not just what we do
Rule of thumb: use a prompt twice, make it a skill. ▶ The deeper point is that skills don't just encode what we do. They encode how we think: review criteria, debugging method, engineering judgment. The stuff that usually lives only in people's heads can now live in a file the team can reuse and improve.

🧩 Session 5

CLI: The Agent's Natural Habitat

This is where we move out of the chat window and into the command line. Not in the sense that you copy terminal output into the model. I mean the AI actually runs the commands itself.

The AI Runs the Commands

From chat → the AI runs the commands

You tell the AI what you want. It runs the build, reads the errors, and fixes the code. Then it loops. That's level 3, and it's a bigger jump than most people expect the first time they see it.

Agent Mode: In Practice

You: "Run the host tests and fix any failures"

Agent: Running `ctest --test-dir build/host-tests`...
       2 tests failed: test_pid_clamp, test_fault_latch
       Reading test source...
       The PID clamp test expects output ≤ 1.0 but
       the implementation doesn't clamp negative values.
       Fixing app/src/control/pid.c...
       Re-running tests...
       All 16 tests pass. ✅
This is what level 3 actually looks like. The AI is using tools: reading files, writing files, executing commands. It's not just generating text into a chat window anymore. You review the diff and decide whether it stays. The AI did the execution, but you still own the judgment.

AI Builds the Tools It Uses

  • Ask AI to build a CLI tool → it does it well
  • Then the AI can use its own tools
  • CLI + Skill = powerful combo
# AI built this, AI uses this
python3 tools/cli.py check-coverage   # exits 1 on gaps
python3 tools/cli.py check-risks      # exits 1 on unmitigated
python3 tools/cli.py sync --check     # exits 1 on drift
▶ LLMs are remarkably good at building CLI tools. The interface is clean: input, output, error code. ▶ So you ask the AI to build a tool, and later the AI can use that same tool itself. You skip the awkward loop where you relay output manually. ▶ And the nice part is that those same tools can also run in CI. Same tool, three paths: human, agent, CI.

HIL as CLI

# Flash, reset, capture UART, check BLE — all one command
python3 tools/hil/reel_board_smoke.py \
  --build-dir build/reel_board \
  --uart-seconds 20 \
  --artifact-dir evidence/hil-latest

When your HIL test is a CLI command, the agent can run it too.

This one is easy to underestimate if you don't live in firmware. When your HIL test is a single CLI command, the agent can run that too: flash the board, capture UART, check BLE services, the whole thing. ▶ Someone still has to physically connect the board. But after that, everything can be scripted. That means the same agent that writes the code can also validate it on hardware.

🧩 Session 6

Context Engineering

The most underrated skill

Context engineering is one of those phrases that sounds a bit buzzwordy until you realize it's actually the practical part. ▶ And firmware engineers have a natural advantage here, because we already think in constraints. That's a big part of why this works well for us.
Context quality > Model quality
This is one of the strongest practical lessons in the whole deck. A mediocre model with great context often beats a frontier model with bad context. The real work is not only writing a better prompt. It's getting the right information in front of the model at the right time.

Project Rules Files

The files

  • CLAUDE.md — Claude Code reads this
  • AGENTS.md — defines roles & workflow
  • copilot-instructions.md — Copilot reads this
  • .cursor/rules/ — Cursor reads these

What goes in them

  • Architecture rules
  • Coding constraints (no heap, ISR-safe)
  • Testing requirements (TDD, simulation-first)
  • Project layout expectations
  • Build & test commands

These files live in your repo. Every AI session starts with the right context automatically.

Every major AI tool has some version of a project rules file. Different names, same principle. The important part is that these files live in the repo, not in somebody's private prompt history. ▶ Set it up once. Every engineer on the team, every session, starts with the right context automatically. No manual briefing. No "remind the AI about our constraints." It already knows.

Curate, Don't Dump

❌ Vibe coding

  • Dump entire repo
  • Hope AI figures it out
  • Retry until it works

✅ Context engineering

  • Project rules in repo
  • Relevant files only
  • Explicit constraints
  • Working examples
"Curate, don't dump"
The bad version of this is: dump the repo in, hope the model figures it out, and retry until something seems to work. ▶ The better version is curated context: relevant files, explicit constraints, good examples. Think of it like a well-written bug report. Everything the reader needs, nothing they don't.

I think of this as a funnel. You start with everything, then narrow down to the relevant files, then the project rules, then the skill, then the actual task. ▶ More context does not automatically mean better context. Focused context is usually better context.

🧩 Session 7

Debugging with AI

Biggest immediate payoff

If I had to pick one place to introduce AI to a skeptical firmware team, I would start here. ▶ Debugging is where you feel the friction most, and where AI often removes it fastest.
AI is a hypothesis generator
AI doesn't debug for you. What it does very well is generate hypotheses faster than you can. Instead of staring at a log for an hour, you can get five plausible root causes in ten seconds. Then you go test them. The judgment is still yours.

Debug Loop

graph LR O["👁️ Observe"] --> H["💡 Hypothesize"] H --> T["🧪 Test"] T --> R["🔧 Refine"] R -.-> O style O fill:#1a1a2e,stroke:#58a6ff,color:#fff style H fill:#16213e,stroke:#58a6ff,color:#fff,stroke-width:3px style T fill:#1a1a2e,stroke:#3fb950,color:#fff style R fill:#1a1a2e,stroke:#58a6ff,color:#fff
This is the same loop you already use. The AI just supercharges the hypothesis step. It has effectively read millions of bug reports and debug sessions. But the test step is still yours. AI does not validate. You do.

Evidence Lives in the Repo

# HYP-001: I2C timeout exceeds control loop budget

## Symptom
Control loop stalls after 30+ minutes of operation

## Hypotheses (ranked)
1. I2C sensor timeout exceeds 10ms budget  ← CONFIRMED
2. Watchdog feed thread starved
3. Stack overflow in fault handler

## Discriminating check
Instrumentation around i2c_transfer():
measured worst-case = 14ms > 10ms budget

⬆️ This lives in the repo, not in a chat window.

This is a real hypothesis document from the Zephyr project. Not in a chat window that disappears when you close the tab. In the repo, version-controlled, reviewable. And when the next engineer hits a similar symptom, the investigation is already there. That's the difference between debugging in chat and debugging with a system.
⚠️ AI does NOT validate — you do

"Logs are gold — invest in structured logging"

Say this clearly: AI does not validate. You do. Never accept an AI diagnosis without evidence. ▶ And logs are gold. The more structured your logging, the more helpful the model becomes. Good logging pays off even more once AI is in the loop.

🧩 Session 8

Agents & Autonomous Loops

This is the point where AI stops feeling like a tool you poke at and starts feeling more like a process that runs.

Definition

graph LR S["⚡ Skill"] --> |"+"| P["📋 Process"] P --> |"+"| L["🔁 Loop"] L --> A["🤖 Agent"] style S fill:#1a1a2e,stroke:#58a6ff,color:#fff style P fill:#1a1a2e,stroke:#58a6ff,color:#fff style L fill:#1a1a2e,stroke:#58a6ff,color:#fff style A fill:#16213e,stroke:#3fb950,color:#fff,stroke-width:3px

An agent = an LLM with access to tools (read, write, execute) and the ability to loop

A chatbot answers. An agent works. That's the key distinction. Skill tells it what to do. Process tells it how. And the loop means it keeps going until the task is done or until it hits a stop condition.

The Ralph Loop

graph TD S["📋 Pick next story"] --> I["👨‍💻 Implement"] I --> C["🧪 Run checks"] C -->|"pass"| CM["✅ Commit + mark done"] C -->|"fail"| F["🔧 Fix based on errors"] F --> C CM --> S CM -->|"all stories done"| DONE["🏁 Complete"] style S fill:#1a1a2e,stroke:#58a6ff,color:#fff style C fill:#1a1a2e,stroke:#58a6ff,color:#fff style DONE fill:#1a1a2e,stroke:#3fb950,color:#fff

Named after Ralph Wiggum — relentlessly failing but persistent. Popularized by Matt Pocock & the aihero.dev community.

This is probably the best-known agent loop right now. Pick the next story from a list, implement it, run checks, fix failures, and keep going. If the checks pass, commit and move on. If they fail, read the errors, fix the code, and re-run. It's simple, but it's a very useful pattern.

Karpathy's Autoresearch

"All LLM frontier labs will do this. It's the final boss battle."
— Andrej Karpathy, March 2026
  • ~630 lines of Python, single GPU
  • Agent modifies training code, trains for ~5 min, evaluates
  • 700 experiments in 2 days
  • Discovered 20 optimizations autonomously

github.com/karpathy/autoresearch — open-sourced March 2026

Karpathy's autoresearch is the large-scale version of the same idea. The agent modifies training code, runs a short experiment, evaluates whether the result improved, and loops. The numbers are the headline: 700 experiments in two days, 20 optimizations found. We are obviously not doing that in firmware today, but the underlying loop is the same.

Bounded Autonomy

graph TD S["🎯 Define: objective + budget + checks"] --> W["✍️ Agent works"] W --> C{"✅ Checks\npassing?"} C -->|"yes"| D{"🏁 Done-when\nmet?"} C -->|"no"| F{"💰 Budget\nleft?"} D -->|"yes"| DONE["✅ Complete"] D -->|"no"| F F -->|"yes"| W F -->|"no"| STOP["🛑 Stop + escalate"] style S fill:#1a1a2e,stroke:#58a6ff,color:#fff style DONE fill:#1a1a2e,stroke:#3fb950,color:#fff style STOP fill:#1a1a2e,stroke:#f85149,color:#fff
This is the part where it's worth being honest about the limitations. Agents do not follow instructions perfectly. They drift, they approximate, and sometimes they get "creative" in exactly the wrong way. The way you make that safe is by bounding the loop. Before it starts, define the objective, the checks it has to run every pass, and a fixed budget. Then it either completes, or it stops and escalates. You never want a confused agent just looping harder.
Agents loop — they don't just answer

"But they don't always follow the script — that's why we bound them"

Watching an agent work can feel a lot like watching a junior engineer work through a checklist, just much faster. ▶ Yegge makes a point I think is real: supervising agents is mentally tiring. Bounded autonomy helps because it gives you clear objectives, fixed budgets, mandatory checks, and escalation when the agent gets stuck instead of silently wandering off.

🧩 Session 9

Roles: One Hat at a Time

Up to now I've mostly talked about one agent doing useful work. Here the shift is from one agent to several specialized ones.

Separation of Concerns for AI

Humans wear many hats.
Agents are more effective wearing one at a time.
As engineers, we switch hats constantly. We plan, code, test, and review, sometimes all in the same hour. Agents are not nearly as good at that. If you ask one AI to plan and implement and review in the same session, it tends to compromise on all three. If you tell it, "your only job is to review and find problems," it goes much deeper. Separation of concerns matters for AI architecture too, not just software architecture.

Example: Agent Team Flow

graph LR PO["👤 Product Owner"] --> PL["📋 Planner"] PL --> DEV["👨‍💻 Developer"] DEV --> VER["✅ Verifier"] VER --> REV["🔍 Reviewer"] style PO fill:#16213e,stroke:#58a6ff,color:#fff,stroke-width:3px style DEV fill:#1a1a2e,stroke:#58a6ff,color:#fff style VER fill:#1a1a2e,stroke:#3fb950,color:#fff

+ optional specialists: researcher, red-team, firmware-architect, safety-auditor...

This is the basic flow I like. Product owner sets the outcome and the why. Planner breaks it into checkable steps. Developer implements. Verifier checks independently. Reviewer looks for hidden risk. Then you bring in specialists only when needed: maybe a researcher for a datasheet, a red team to challenge the plan, or a firmware architect when interfaces matter. Each role has one job, and the product owner keeps the thread coherent.

Being Honest About Agents

What works

  • Focused single-role tasks
  • Clear done-when criteria
  • Small, bounded slices
  • Skills for domain guidance

What doesn't (yet)

  • Agents drift from instructions
  • Context windows force session breaks
  • Turn budgets exhaust mid-task
  • Creative "helpfulness" = scope creep
Let me be candid about where agents are today. They work well on focused tasks, with one role, clear criteria, and small slices. But they also drift. They hit context limits. They run out of turn budget halfway through something. And "creative helpfulness" is often just scope creep in disguise. The answer is not to avoid agents. It's to bound them properly, keep the slices small, and review what they produce.
"One agent = one responsibility"

Coordination is the system
The short version is: one agent, one responsibility. ▶ The value is not in any single agent being magical. The value is in the handoffs and feedback loops between them. In other words, the coordination is the system.

🧩 Session 10

Systems Thinking

This is the big-picture session where the earlier pieces start fitting together.

We Design Systems of Work

From writing code → designing systems of work

Yegge predicts that IDEs will be heavily displaced by agent interfaces. Maybe his exact timeline is right and maybe it isn't, but the direction feels clear. For firmware, the code still matters because it runs on real hardware. But more and more, the thing we invest in is the system that produces, checks, and improves that code.

Three Ideas

  • Validation > Generation
  • Feedback loops
  • Decomposition
▶ First: validation matters more than generation. AI can generate code all day. Our value shifts toward defining what "correct" means and proving it. ▶ Second: feedback loops. CI feeds back into the work. Skill improvements feed forward into the next task. ▶ Third: decomposition. Big problems become much more manageable when you break them into smaller pieces, each with its own agent, skill, and verification.

System View

IEC 62304: AI-Written Regulatory Docs

The entire 13-document IEC 62304 Class B set was:

  1. ✅ Authored by AI from codebase analysis
  2. ✅ Audited by AI (safety-auditor role, notified-body perspective)
  3. ✅ Remediated by AI across 11 parallel slices
  4. ✅ Re-audited by AI to verify closure

Initial audit: 26 findings

7 major · 11 minor · 8 observation

After remediation: 18 closed

8 partially closed (process, not content)

This was one of the results that surprised me most. The AI generated the full IEC 62304 Class B document set from the codebase, and then a different AI role reviewed it from a notified-body perspective. That audit found 26 real findings. After remediation across 11 parallel slices, 18 were closed. The remaining ones were mostly process gaps: named human reviewers, human sign-off, things like that. And that's exactly as it should be. AI is a tool here. The responsibility for documentation, verification, and regulatory compliance still sits with us.

When the context window resets, the work packet keeps the thread alive. If a new engineer joins, they can read the brief and plan. If someone asks why a decision was made, the evidence is there. That's the difference between using AI in a chat window and building a system around it.

🖥️ Demo Time

Demo 1: Skill-Driven Code Review

🎯 What to show

  1. Open a firmware source file with a subtle bug (e.g., missing ISR guard)
  2. Ask the AI to review using the firmware review skill
  3. Show how it catches the issue and suggests a fix
  4. Show the skill file that guided the review

💬 What to say

"The review follows our checklist — memory safety, concurrency, edge cases — because the skill tells it to. Without the skill, it gives generic feedback."

For this one, open a firmware file with a subtle bug, maybe a missing ISR guard or an unchecked return value. Ask the AI to review it using the skill, then show the skill file itself and make the point that it is just a markdown file driving the behavior. The thing that usually lands with people is the contrast between with-skill and without-skill.

Demo 2: The Ralph Loop

🎯 What to show

  1. Show a list of 3 small user stories
  2. Launch the agent loop
  3. Watch it: implement → test → fail → fix → pass → next story
  4. Show the commit history: one clean commit per story

💬 What to say

"Three stories, zero typing. The agent picks each one up, writes code, runs tests, fixes failures, commits when green. We review the diffs."

Prepare three small, well-defined user stories and let the agent work through them live. Ideally the audience sees the whole loop: implement, test, fail, fix, pass. Then show the commit history. If time is tight, pre-record it and narrate. The key line here is: "Three stories, zero typing from me, but I still review every diff."

Demo 3: "Grill Me" Skill

🎯 What to show

  1. Describe a feature idea (e.g., "add BLE OTA updates")
  2. Say "grill me about this plan"
  3. Show the AI interrogating you: edge cases, failure modes, timing
  4. Show how it reads the codebase to answer its own questions

💬 What to say

"I didn't think of half these questions. The AI is stress-testing my plan before I write a single line."

This one tends to be the crowd-pleaser. Pick a feature the audience actually cares about, BLE OTA updates for example, and say "grill me." Then let the AI probe the plan: failure modes, timing, rollback, edge cases. The reaction you usually get is, "I didn't think of half those questions," and that's exactly the point.

🧱 Final Takeaways

Let me wrap up with the handful of things I think are actually worth keeping from all of this.

The 12 Rules

  1. Give the agent a role
  2. Add constraints
  3. Keep tasks small
  4. Ask for process
  5. Build skills
  6. Put project rules in the repo
  7. Reuse everything
  8. Verify outputs
  9. Think in bounded loops
  10. Use specialized roles
  11. Context matters most
  12. Design systems, not prompts
I'm not going to read all twelve of these word for word, but this is the checklist I keep coming back to: give the agent a role, add constraints, keep tasks small, ask for process, build skills from reused prompts, put project rules in the repo, and always verify. Most of these feel obvious once you've been doing it for a while. They are much less obvious when you're starting out.

Firmware Teams Have an Advantage

  • Timing matters — AI doesn't understand budgets unless you tell it
  • Hardware is real — compilation ≠ correctness on device
  • We already think in constraints — ISR safety, memory, timing
  • HIL as CLI — when tests are commands, agents can run them
Firmware teams are actually in a strong position here, because we're already used to thinking in constraints. ▶ Timing matters, and the model won't know your budget unless you state it. Hardware is real, so code that compiles is still not the same thing as code that works on device. ▶ But the upside is that ISR safety, memory limits, timing budgets, all of that already lives in our heads. That makes context engineering feel more natural for firmware engineers than it does for a lot of other disciplines. ▶ And when your HIL setup can be driven from the CLI, agents can actually close that loop for you.
"We are not just using AI — we are extending it with our engineering system"
The model itself is powerful, but generic. What makes it useful for firmware, for Össur, for bionics, is what we build around it: the skills, the project rules, the engineering method. That's the real advantage. Not the raw model, but the system we wrap around it.

I'll leave you with this thought. Ten years ago, would you write firmware without version control? Five years ago, without CI? AI feels like the next thing in that line to me, not because it's fashionable, but because it is genuinely useful when you use it properly. Not vibe coding. Context engineering. Skills. Bounded loops. Systems. The engineers who learn to build those systems are going to move faster and build better products. Thank you.
